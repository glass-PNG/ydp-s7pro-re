# 3346:1000 下载模式协议（实测复原）

设备进入方式：**按住「回城键」再插 USB**，屏幕出现彩色方格，枚举为
`VID_3346&PID_1000`，接口是两个 CDC-ACM（通信口 + 数据口，bulk 512B）。
Windows 自带 `usbser.sys` 即可，**不需要装厂商的 libusb 驱动**
（装了反而抢不到端点 —— 我们用 libusb-1.0 在这台设备上 bulk 全废，SET_LINE_CODING 能通）。

串口参数：`921600 8N1`，**打开前必须把 DTR/RTS 置低**，
否则 pyserial 默认拉高 DTR 会让设备退出下载模式。

---

## 1. 两种帧头（关键）

同一固件对数据面和控制面使用不同的帧头，长度固定：

### 数据面：8 字节头（token `0x00`）

```
+--------+--------+--------+--------+--------+--------+--------+--------+
| token  | len_hi | len_lo | addr[4]| addr[3]| addr[2]| addr[1]| addr[0]|
+--------+--------+--------+--------+--------+--------+--------+--------+
  1B       1B       1B       <---------- 5B 大端 40 位地址 ---------->
```
`len = 8 + len(payload)`，payload 上限 **256 字节**。
设备侧语义：`memcpy(addr, payload, len - 8)`。

### 控制面：16 字节头（token `0x81/0x82/0x83/0x0a/0x0c`）

```
+--------+--------+--------+--------+--------+--------+--------+--------+
| token  | 0x00   | 0x10   | addr[4]| addr[3]| addr[2]| addr[1]| addr[0]|
+--------+--------+--------+--------+--------+--------+--------+--------+
|                         size (8B 小端)                                  |
+-------------------------------------------------------------------------+
```
第 2 字节恒为 0，第 3 字节恒为 `0x10`（即头部长度 16）。
`size` 只在 `0x81/0x82/0x83` 里有意义。

> 常见误解：把 8 字节头套到 `0x82` 上、或把 16 字节头套到 `0x00` 上，
> 表现都是「设备复位」或「只写进去 8 个字节」。这个坑我们踩了很久。

## 2. CRC 与 ACK

- CRC：**CRC-16/XMODEM**（多项式 0x1021，init 0x0000，无 final xor），
  覆盖「帧头 + 载荷」整包。`crc16(b"123456789") == 0x31C3` 可自检。
- 应答恒 16 字节：

```
+--------+--------+--------+--------+--------+--------+--------+--------+
| 0x00   | 0x00   | crc_hi | crc_lo | 0x00   | 0x00   | token  | count  |
+--------+--------+--------+--------+--------+--------+--------+--------+
|                        aux / 数据（命令相关）                            |
+-------------------------------------------------------------------------+
```
`count` 是设备侧**单调自增的命令计数器**（每次 ACK +1，可用于判断设备是否复位）。
`0x0c` 例外：**没有 ACK**，发出后直接开始流 1 MiB 数据。

## 3. token 表（全部来自真机实测）

| token | 帧头 | 请求 | 设备行为 | 状态 |
|---|---|---|---|---|
| `0x00` | 8B | addr + payload | 写内存，回 16B ACK | ✅ |
| `0x01` | 16B | addr + payload | 仅 ACK（置标志位） | ✅ |
| `0x02` | — | — | 落未知分支 | ⚠️ 未实现 |
| `0x03` | 16B | addr | **立即掉 USB，随后重启** | ❌ |
| `0x06` | 16B | ASCII 命令串 | ACK 但不执行（不是 shell） | ⚠️ |
| `0x0a` | 16B | addr | 把上次 `mmc read` 的缓冲发回；失败也照发 | ⚠️ |
| `0x0c` | 16B | addr | `mmc dev 0 1` + `mmc read 0x… 0 0x800` + 发 1 MiB | ✅ |
| `0x81` | 16B | addr + size | 写内存（低地址为 memcpy，高地址走 DMA 结构体） | ⚠️ |
| `0x82` | 16B | addr + size | 读内存，直接回 `size` 字节 | ✅ |
| `0x83` | 16B | addr + 64B 结构体 | 组 `mmc read` 并执行 | ⚠️ |

### 3.1 `0x83` 的结构体

写在 `addr` 处（普通做法是 `0x93200000`）：

```c
struct mmc_req {   // 小端
    uint32_t reserved;   // +0
    uint32_t size;       // +4  字节数，内部向上对齐 512 后 >>9 得扇区数
    uint64_t offset;     // +8  字节偏移，>>9 得起始扇区
};
```

设备侧等价于：

```c
snprintf(cmd, "mmc read %p 0x%llx 0x%x", 0x93200040, offset >> 9, size >> 9);
run_command(cmd);
// 返回值：成功 = 扇区数，失败 = 0
```

随后 `0x0a` 若发现返回值为 0，会打印错误但仍然把旧缓冲发回来
—— 这就是为什么「读用户区」看起来能收到数据，其实是上一次的残留（全零/全 0xFF）。

### 3.2 `0x82` 的长度怪癖

实测 `size` = 16 / 64 / 128 / 256 / 4096 → 正常返回；
`size` = 512 / 1024 / 2048 → **一个字节都不回**。
批量读请用 4096。

## 4. 地址映射

设备侧 `0x82` 读回的内容与 `boot0` 硬件分区高度对应：

```
VA = boot0_offset + 0x7FFFF000        (适用于 boot0 里那份 fip/u-boot 副本)
```

验证：`0x82(0x80000000, 16)` 返回 `0e62b6528f1080d2…`，
而 boot0 偏移 `0x1000` 处是 `0e40b6528f1080d2…`（仅运行期改写的立即数不同）。
`0x82(0x80000100, 16)` 返回两个字面池指针 `0x80007000` / `0x80011000`，与 BL2 一致。

**但注意**：运行中的镜像与 boot0 里那份备份**不是同一个构建**
（boot0 fip 头 cksum `0xcafeb37a`，OTA 包内 fip 是 `0xcafee953`），
所以按 boot0 静态反汇编得到的地址不能直接当运行地址用。

## 5. 内存布局（实测）

| 地址 | 内容 |
|---|---|
| `0x80000000+` | ARM TF-A（BL2/BL31），可见 `PANIC at PC : 0x`、`std_svc`、`EL1 supports AArch64-only` |
| `0x80800000` | 我们自己上传 fip 的位置（631,808 B，2.2 s，275 KB/s，回读校验通过） |
| `0x82000000` / `0x84000000` / `0x88000000` / `0x90000000` | DDR 训练图案 `55 55 aa aa 54 54 a8 a8…` |
| `0x93000000` / `0x93300000` | 空 |
| `0x93200000` | 协议用的命令结构体 / 读缓冲（`mmc read` 目标是 `0x93200040`） |
| `0x9AA00000` | 二级核（C-SKY）媒体固件，与 `yoc.bin` 偏移 `0x200` 一致 |

> 结论：下载模式固件的协议处理代码**不在可读 DRAM 里**（跑在片内 SRAM），
> 所以改 DRAM 里的字符串（例如把 `mmc dev 0 1` 改成 `mmc dev 0 0`）没有任何效果。

## 6. 一键复现（伪代码）

```python
import serial, serial.tools.list_ports

def open_port(com):
    s = serial.Serial()
    s.port = com
    s.baudrate = 921600
    s.dtr = False          # 必须在 open 之前
    s.rts = False
    s.timeout = 5
    s.open()
    return s

def crc16(data, crc=0):
    for b in data:
        crc ^= b << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc

def frame8(tok, addr, payload):
    return bytes([tok, ((8+len(payload)) >> 8) & 0xFF, (8+len(payload)) & 0xFF,
                  (addr >> 32) & 0xFF, (addr >> 24) & 0xFF, (addr >> 16) & 0xFF,
                  (addr >> 8) & 0xFF, addr & 0xFF]) + payload

def frame16(tok, addr, size, payload=b""):
    return bytes([tok, 0, 0x10,
                  (addr >> 32) & 0xFF, (addr >> 24) & 0xFF, (addr >> 16) & 0xFF,
                  (addr >> 8) & 0xFF, addr & 0xFF]) + size.to_bytes(8, "little") + payload
```

发送后读 16 字节 ACK，校验 `ack[2:4] == crc16(pkt)` 且 `ack[6] == token`。

## 7. 会挂死的操作（务必避开）

- `0x82` 读 `0x0`、`0x0E000000`、`0xC0120000` 等非 DDR 地址 → 设备挂死，
  之后端口被驱动独占（`PermissionError(13, '拒绝访问')`），**只能物理拔插**。
- 一次大流量命令（`0x0c` 1 MiB）之后立刻读 `0x82`，会读到流残余的乱码，
  必须先 `reset_input_buffer()` 并等安静（我们用一个「读 `0x80000000` 必须回
  `0e62b652…`」的同步探针判断设备是否回到可通信状态）。
- `0x83` + 大 size（1 MiB）会把 loader 弄卡，表现是写入超时。
